# Agent Loop

## Overview

The agent isn't a single API call — it's a loop. The AI responds, optionally requests tool calls, we execute those tools, feed the results back, and the AI responds again. This repeats until the AI stops requesting tools.

```
user message
    → LLM responds (text + optional tool calls)
    → execute each tool
    → feed results back to LLM
    → LLM responds again
    → ... repeat until no tool calls
    → return final text
```

---

## The Provider Interface

Supporting multiple AI providers (Anthropic, OpenAI) without duplicating the loop logic is done with a Go **interface**. An interface defines a set of methods that a type must implement — any type that has those methods satisfies the interface automatically.

```go
type Provider interface {
    Complete(system string, history []Turn, tools []ToolDef) (
        text string, calls []ToolCall, inputTokens int, outputTokens int, err error,
    )
}
```

`AnthropicProvider` and `OpenAIProvider` both implement `Complete` with their own HTTP logic, but the agent loop only ever calls `a.provider.Complete(...)` — it doesn't know or care which one it's talking to.

Adding a new provider means writing a struct that implements `Complete` and registering it in `NewProvider`.

## The Loop in Agent.Run

```go
func (a *Agent) Run(history []Turn, userMsg string, onTool OnToolFn, confirm ConfirmFn) (string, []Turn, error) {
    history = append(history, Turn{Role: "user", Text: userMsg})

    for {
        text, calls, inputTokens, outputTokens, err := a.provider.Complete(...)

        history = append(history, Turn{Role: "assistant", Text: text, Calls: calls})

        // emit token count to the UI
        if onTool != nil && inputTokens > 0 {
            onTool(fmt.Sprintf("%d in · %d out", inputTokens, outputTokens))
        }

        if len(calls) == 0 {
            return text, history, nil  // done
        }

        // execute tools and collect results
        var results []ToolResult
        for _, call := range calls {
            // ... confirm if needed, execute, collect result
        }
        history = append(history, Turn{Role: "user", Results: results})
    }
}
```

The full conversation history is passed to every `Complete` call. This is how LLMs maintain context — they don't have internal memory; they receive the whole thread each time.

## The Tool System

Tools live in `agent/tools.go` in a map:

```go
var toolBox = map[string]tool{
    "read_file":      { Def: ..., Execute: func(...) string { ... } },
    "write_file":     { Def: ..., Execute: func(...) string { ... }, RequiresConfirmation: true },
    "search_files":   { ... },
    "list_directory": { ... },
    "run_command":    { ..., RequiresConfirmation: true },
}
```

Each `tool` has:
- **`Def`** — the JSON schema sent to the LLM describing what the tool does and what parameters it takes
- **`Execute`** — the actual Go function that runs when the LLM calls the tool
- **`RequiresConfirmation`** — if true, the user must approve before `Execute` is called

The `fileTools` slice (derived from `toolBox`) is sent to every `Complete` call so the LLM knows what tools are available.

## Confirmation Flow

`write_file` and `run_command` require confirmation. The challenge is that the agent loop runs in a goroutine, but the UI must receive user input on the main Bubbletea thread.

This is solved with a pair of channels:

```go
confirmMsgCh      chan confirmRequestMsg   // goroutine → UI: "please confirm this"
confirmResponseCh chan bool                // UI → goroutine: "yes" or "no"
```

The agent goroutine blocks on `<-confirmResponseCh` while the UI waits for the user to press `y` or `n`, then sends the result. The goroutine resumes with the answer.

```go
// In the agent goroutine:
confirmMsgCh <- confirmRequestMsg{msg: "writing main.go", preview: diff}
approved := <-confirmResponseCh  // blocks here

// In the TUI (on 'y' keypress):
m.confirmResponseCh <- true
```

The diff shown during confirmation is generated by `generateDiff` in `agent.go`, which runs `git diff --no-index` on the current file vs the proposed new content written to a temp file.

## Token Tracking

Each `Complete` call returns `inputTokens` and `outputTokens` from the API response. The agent emits these immediately via `onTool`:

```go
onTool(fmt.Sprintf("%d in · %d out", inputTokens, outputTokens))
```

In the TUI, `onTool` sends to `m.toolCh` (a buffered channel), which gets picked up as a `toolUpdateMsg` and appended to the feed as a `msgKindAction` entry. Token lines appear in the same dim style as tool calls so they don't distract but are always visible.
